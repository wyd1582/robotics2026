项目 1：让机械臂模仿专家，再修复它访问过的失败状态

量化类比：复现一个已知规则策略，用监督模型模仿它；将模型投入执行后发现分布变化，再有针对性地补充样本。机器人这里的专家是控制器，标签是动作。

任务：两关节机械臂将末端移向随机目标。环境为真正的 MuJoCo `Reacher-v5`；状态包含关节角的 sin/cos、目标位置、关节速度、末端到目标的向量。不是视觉模型，没有抓取或接触。

数据流：专家控制器在仿真中执行 → 保存原始轨迹 → 检查有限值与episode分隔 → 用训练集统计量归一化 → 拟合行为克隆模型 → 保存/加载 → 独立初始条件下执行 → 收集学生访问状态的专家动作标签 → 再训练 → 配对比较。

先运行：

```bash
uv run python loop01_imitation.py --quick
```

然后打开新 run 的 `bc.gif`、`teacher.gif`、`dagger.gif`。先看发生了什么，再看指标。动画从 MuJoCo 实际状态绘制，按每个仿真 step 40ms 播放，约为模拟实际时间的半速。

数据文件字段：

| 字段 | 含义 | 容易犯的错误 |
|---|---|---|
| obs / next_obs | 动作前/动作后的观测 | 将 next_obs 作为当前输入导致未来信息泄漏 |
| expert_action | 专家在当前状态给出的标签 | 把有噪声的 executed_action 当成专家标签 |
| executed_action | 真正进入模拟器的命令 | 忽略它与标签的区别，会误判数据质量 |
| episode / step | 轨迹与时间步 | 随机拆帧导致训练/验证相邻帧泄漏 |
| sample_time | step × 0.02 秒 | 跨 episode拼时间，或当成传感器到达时间 |
| terminated / truncated | 自然终止/时间上限 | 把时间上限当作物理终止 |

这里的数据由模拟器产生且结构干净，因此第一遍是做质量门禁，不是强行删除一些数据。第二遍可以在副本注入 NaN、动作错位或缺帧，再检验门禁与模型变化，原始数据保持不变。

行为克隆学的是 π(o)≈a_expert。脚本对动作也按训练集统计量标准化；训练 loss 是标准化动作 MSE，验证 loss 是实际命令单位的 MSE，两者数值不能直接横比。

专家不是“全知最优”。它使用两连杆逆运动学和 MuJoCo 逆动力学。验证版本里的 actuator gear=200，发送给环境的 ctrl 与实际关节力矩不能混为一谈；这是本体接口语义的第一课。学生仅访问标准观测，专家调用仿真内部物理量，不应把专家能力误归给学生。

纠正实验采用单轮 DAgger 式数据聚合：在学生策略访问的状态请求专家标签，采集时20%概率执行专家、80%执行学生，然后与原始数据合并。它是方法演示，不是论文完整迭代/理论保证的复现。

脚本自动比较：

| 组别 | 新标签 | 额外训练更新 | 为什么需要 |
|---|---:|---:|---|
| bc | 无 | 无 | 原始基线 |
| more_updates | 无 | U | 排除“仅仅多训练了” |
| more_expert | 普通专家演示 | U | 排除“仅仅数据量更多” |
| dagger | 学生访问状态的专家纠正 | U | 研究数据分布/恢复覆盖是否有价值 |

后3组都从相同BC参数出发，使用相同额外更新预算。more_expert 与 dagger有相同episode数、时长与标签查询数量；采集轨迹分布不同正是实验干预。老师计算量/未来真人人工成本不能假定相同，做真实预算报告时需要另测。

评测包括0步和2步观测延迟。2步对应40ms，历史缓存在每个episode重置；起始时以reset观测填充历史，需把这一约定写入报告。teacher/random/zero只有无延迟参考，不能把它们当延迟鲁棒性的公平控制器对照。

主要指标为最后10步的平均末端距离，越小越好；另外保存Gym回报和自定义成功（平均距离<2.5cm）。没有将训练loss当机器人成功，也没有冒充官方成功指标。

第一遍作业：指出collect、fit、evaluate分别对应raw data、建模、backtest的哪一段；解释相同离线MSE为何会产生不同rollout；解释某些情况下补数据反而变差。

第二遍只选一个变量：

1. `--episodes 40/80/160`：更新预算固定，比较样本量；同时报告每条数据平均被看到次数。
2. 修改采集 beta：0/0.2/0.5，比较纠正状态覆盖与采集干预成本。
3. 增加延迟1/4步：画退化曲线，不能只比较最好的一项。
4. 只在episode内错配 observation/action，边缘帧一致截断；明确这是训练错位，不是部署延迟。

第三遍贡献题：设计一个“什么时候请求专家纠正”的规则，用相同标签查询预算比较随机请求与规则请求。需要记录每次查询、遗漏失败与指标置信区间。先在这里验证，再检查真实开源仓库是否已有同类功能。

口试：BC优化哪个分布上的误差？DAgger为何改变训练状态分布？如果dagger赢过bc却没赢过more_updates，你能得出什么结论？
